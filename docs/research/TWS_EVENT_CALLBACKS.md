# TWS event callbacks: source findings for a read-only UI design

Researched 2026-09-28 against IBKR documentation. The older `interactivebrokers.github.io` API guide marks itself deprecated; its detailed behavior below should be checked against the installed TWS/API version in paper trading.

## Positions and trades

- `reqPositions()` subscribes to all accessible-account positions. It sends the initial set, then `positionEnd()`, and thereafter `position()` when a position changes. `reqPositionsMulti()` can target an account/model and has its own end marker. Large adviser/master-account configurations have limits on `reqPositions()`. [IBKR positions](https://interactivebrokers.github.io/tws-api/positions.html); [IBKR Campus portfolio lesson](https://ibkrcampus.com/campus/trading-lessons/python-account-portfolio/).
- `execDetails()` is delivered for full and partial fills; `commissionReport()` follows separately. IBKR says execution corrections arrive as another `execDetails()` with a changed execution ID. `reqExecutions()` supplies a bounded historical reconciliation with `execDetailsEnd()`; default history is since midnight, and TWS Trade Log settings can extend it to seven days (Gateway cannot change that setting). [IBKR executions and commissions](https://interactivebrokers.github.io/tws-api/executions_commissions.html).
- An initial position snapshot cannot by itself establish that a position is *newly acquired*. Compare only after the initial `positionEnd()` baseline, and distinguish contract quantity changes from a genuinely new account/contract key. This is a design inference from the callback semantics above.

## Orders and brackets

- `openOrder()` contains the contract, order and order state, including price and quantity fields; `orderStatus()` carries status, filled and remaining quantities, and identifiers. `openOrderEnd()` marks the end of an order snapshot. `orderStatus()` may be duplicated and is **not guaranteed for every status transition**; IBKR recommends also monitoring `execDetails()`. [IBKR open orders](https://interactivebrokers.github.io/tws-api/open_orders.html); [IBKR order submission](https://interactivebrokers.github.io/tws-api/order_submission.html).
- `reqAllOpenOrders()` gets a **one-time snapshot**, not an ongoing subscription, of current API open orders across clients. `reqOpenOrders()` targets the same client ID; with client ID 0 it binds existing manually entered TWS orders. `reqAutoOpenOrders(true)` is client-0-only and binds future manual TWS orders for ongoing updates. A configured Master Client ID receives automatic order updates across API clients. [IBKR open orders](https://interactivebrokers.github.io/tws-api/open_orders.html); [IBKR EClient reference](https://interactivebrokers.github.io/tws-api/classIBApi_1_1EClient.html); [IBKR initial setup](https://interactivebrokers.github.io/tws-api/initial_setup.html).
- Binding is **not observation-only**. It assigns an API order ID and makes a manual order modifiable/cancellable by client 0. IBKR's older guide says binding could cancel/resubmit an exchange-working order and affect queue position, as of TWS 970. `reqAllOpenOrders()` does not bind. An account-wide permanent ID (`permID`) identifies an order more stably than a client-specific API order ID. [IBKR modifying orders](https://interactivebrokers.github.io/tws-api/modifying_orders.html). Therefore a design must not enable manual-order binding merely to achieve push notifications without explicit safety review.
- The older IBKR Initial Setup guide explicitly says **order information is unavailable when TWS API Read Only mode is enabled**. A newer IBKR Campus setup lesson says Read-Only blocks all API orders, without confirming order-data behavior. This discrepancy makes order/bracket monitoring under strict Read-Only a **paper-TWS feasibility test**, not an assumed capability. [IBKR initial setup](https://interactivebrokers.github.io/tws-api/initial_setup.html); [IBKR Campus setup lesson](https://ibkrcampus.com/campus/trading-lessons/installing-configuring-tws-for-the-api/).
- A bracket is not one atomic event in these APIs: its legs arrive as separate orders and status/execution callbacks. Inferring a transmitted bracket requires correlating parent/child references, account, contract, permanent IDs and transmission/working states, then confirming the complete leg set. This is a design inference from the separate `openOrder()` and `orderStatus()` APIs; do not alert on one observed leg as a complete bracket. [IBKR open orders](https://interactivebrokers.github.io/tws-api/open_orders.html); [IBKR order submission](https://interactivebrokers.github.io/tws-api/order_submission.html).
- `reqCompletedOrders()` is available for completed-order reconciliation, while the older active-order guide says active-order requests do not return fully filled or cancelled orders. [IBKR EClient reference](https://interactivebrokers.github.io/tws-api/classIBApi_1_1EClient.html); [IBKR open orders](https://interactivebrokers.github.io/tws-api/open_orders.html).

## Connectivity and safety implications

- IBKR error code 1100 means TWS lost backend connectivity; 1101 means restored with data lost; 1102 means restored with data maintained. Code 1300 means the socket port changed and the client connection drops. A UI should mark state stale on interruption and reconcile before presenting event-derived state as current. [IBKR message codes](https://interactivebrokers.github.io/tws-api/message_codes.html).
- The API/TWS socket can close independently of backend connectivity; `connectionClosed()` reports that socket closure. [IBKR EWrapper reference](https://interactivebrokers.github.io/tws-api/interfaceIBApi_1_1EWrapper.html).
- IBKR advises monitoring `error()`, `orderStatus()`, `openOrder()` and `execDetails()` for order rejection/cancellation and execution. [IBKR automated-system considerations](https://interactivebrokers.github.io/tws-api/automated_considerations.html).

## Recommended feasibility questions for paper TWS

1. With Read-Only enabled, do `reqAllOpenOrders()`, `openOrder()` and `orderStatus()` actually expose manual brackets and their later price edits on the project's TWS/API versions?
2. Without `reqAutoOpenOrders(true)` or any binding, can a nonzero Master Client ID observe a *new* manual TWS bracket promptly, or only after a snapshot request?
3. Are all bracket legs, parent IDs, `permID`s, quantities, order states and price edits visible consistently before and after reconnect?
4. Which callbacks appear for manual fills, partial fills, cancellation, outside-app edits and execution corrections under the intended account/client configuration?

Until these are answered, positions can be designed as an event stream, while manual-bracket alerts should retain a snapshot/reconciliation fallback and explicit uncertainty state.
